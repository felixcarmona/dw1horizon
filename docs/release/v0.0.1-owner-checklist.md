# v0.0.1 owner checklist

Run these commands only when cutting the release. The preparation task does not
create tags, push, upload artifacts or deploy. Player notes:
[`v0.0.1-notes.md`](v0.0.1-notes.md), accepted by `release.py --notes-file`.

## Before the tag

1. Finish the source review and recheck the final literal publication gate:
   a green older package does not clear a newly generated package. Resolve any
   remaining publication blockers before uploading playable artifacts.
2. Decide the repository to publish. If publishing the clean/squashed repository,
   finish the reviewed source transfer first. Build on that repository's actual
   final commit: private-repo packages fail Pages commit identity validation.
   A development disc embeds its dev version. Use the sealed reuse procedure below
   to change that fixed buffer and recompute its deltas; copying the old disc or
   changing only manifest metadata is insufficient. Keep reports outside the
   tracked tree or under ignored `build/`.
3. Confirm a clean checkout and the intended commit:

   ```sh
   git status --ignore-submodules=all
   git log --oneline -5
   python3 tools/release.py --preflight-only
   ```

   The checked-in corpus already contains `20261027-d2796814.json/.mcd`.
   A first public release does not require an empty corpus or a card already named
   v0.0.1: the mandatory check tests every existing card against current tags and
   story locks. Never erase the
   corpus or renumber tags/locks to make this check pass. Emulator checks and
   recording a new card are separate options, not prerequisites for the file gate.
4. Verify native prerequisites from the patcher guide: ten clean registered input
   images (seven DW1 bases and three source games), USA `extracted/` and its private
   extraction metadata `build/digimonworld.xml`, mkpsxiso,
   `dw-build` Docker image, generated decomp inputs and browser test dependencies.
   Python must be 3.10+. The script creates a private pinned decomp worktree.
   The existing browser runner currently expects the local puppeteer installation
   under `build/stage9/node/node_modules` and `/snap/bin/chromium`.

## Fast cut from a verified final proof

Commit all final code **before** producing commit X's final proof.
The reuse check compares the entire tracked git tree, including tooling and web
code. A different commit with an identical tree is accepted; an older source tree,
a dirty package commit, a different clean-publication tree or a changed bundle is
refused. Never relabel an older package or cache to bypass this check.

Finish X's mandatory native 2 MB heap/story, offline selftest, save, independent
seven-base output and publication proofs. Retain its complete package, all seven
`everything-BASE.bin` outputs (`make-release --keep-outputs DIR`), native build
metadata (`derived/{manifest,plan}.json`, `exe*/SLUS_010.32.elf.map`, text banks,
and language overlays), and its verified engine. This path reuses the existing
engine graph; it does not record a missing engine. Finish the final proof's browser
check before sealing. Keep all these artifacts unchanged until the cut succeeds.

From X's clean worktree, before the owner creates the release tag, seal the proof:

```sh
python3 tools/release.py --prepare-reuse \
  --reuse-package "$PWD/build/package" \
  --reuse-outputs "$PWD/build/release-images" \
  --reuse-build "$PWD/build/everything" \
  --reuse-engine "$PWD/build/engine" \
  --reuse-bases "$PWD/build/base-inputs.json" \
  --reuse-sources "$PWD/build/source-inputs.json" \
  --out "$PWD/build/releases/verified-X"
```

Adjust paths to the actual final proof. Bases/sources JSON files are objects mapping
base/game keys to absolute original image paths. This command builds nothing. It
requires the package's recorded commit to have X's exact tree, an already passing
publication report, the actual registered input hashes, all seven manifest output
hashes and verified hole hashes, and an engine embedding the exact package. It
reruns publication on a private package snapshot and writes `reuse.json` with the
tree hash and SHA-1 inventories of every retained artifact. It leaves the proof
owner's package, engine, metadata and images unchanged. `reuse.json` is a trusted
local handoff, not a signature or a replacement for the preceding heavy gates.

Then, from a clean worktree with **the same git tree**, the owner tags and cuts:

```sh
git tag -a v0.0.1 -m 'Digimon World Horizon 0.0.1'
python3 tools/release.py v0.0.1 \
  --reuse-from /absolute/path/to/build/releases/verified-X \
  --jobs 4 --out "$PWD/build/releases/v0.0.1"
```

The cut validates the complete seal and all inputs again. It copies artifacts,
changes only the executable's symbol-located 32-byte title version buffer and
its affected sectors' EDC/ECC, recomputes each base's executable delta diff/extra
blocks, compacts away superseded bytes, and updates manifest version/date/commit,
patch size/hash and all seven output pins. Every non-executable file and license
sum must remain identical. Each resulting package is streamed through the writer
for all seven bases using retained, individually hash-checked derived files;
no derive jobs or temporary full-image writes occur in this verification.

It reruns the publication gate, runs the **shipped USA writer** outside the checkout
in `python:3.10-slim` with no network or site packages, repacks the existing engine
graph, and requires a complete independent USA browser derivation and OPFS SHA-1.
The Python 3.10 gate uses the retained verified holes; it does not claim a fresh
CLI derive replay. The browser does derive them again. No native/decomp build,
model/import recording, selftest fixture build or engine graph recording runs.
Default save-file and small regression checks still run. Docker must already
have `python:3.10-slim`; browser prerequisites remain required. No performance
claim is made for an unmeasured end-to-end cut; this removes the measured cold
build/record stages, leaving hashing, writing and the browser run.

`--skip-browser`, emulator-save checking and save recording are refused on reuse;
use the full pipeline for new recordings. All mismatches fail closed with no cold
build fallback. Use a new output directory after failure. Retain `summary.json`,
`restamp-proof.json` (all seven before/after file and license SHA-1s),
`package-sums.json`, `browser.log`, package/ and engine/. The local outputs/ are
private proof artifacts; the release archive contains only package/. Remove the
seven copied outputs after their evidence and release have been retained.
Deployment/publication remain explicit opt-ins as described below.

## Tag and build locally

```sh
git tag -a v0.0.1 -m 'Digimon World Horizon 0.0.1'
python3 tools/release.py v0.0.1 --jobs 4 --out "$PWD/build/releases/v0.0.1"
```

The annotated tag must already point at HEAD. Use a new output directory on each
attempt. Do not change commits, tags or files while the build runs. The default
command does not deploy or publish. Retain `summary.json`, browser.log, package/
and engine/ from the successful run. The script runs, in order:

- clean/tag identity; published-save file gate; fast regressions;
- registered input checksums; private decomp patch replay and source extraction;
- everything build and executable/story heap gates for original 2 MB hardware;
- original dialogue and default-model fixtures reconstructed from verified inputs;
  offline selftest; seven-base package construction and its mandatory save gate;
- shipped standalone USA and Japan Rev 1 applies, with independent image SHA-1s;
- candidate engine build, graph-keyed recorder reuse, local USA browser build and
  independent OPFS checksum comparison;
- package-only archive and SHA-1 inventory; final unchanged checkout check.

`--save-check-emu` adds Continue/resave checks for existing corpus cards.
`--record-save /absolute/seed.mcd` records into OUT/save-corpus without changing
the tagged checkout; review the new pair for a later corpus commit. Keep memory
card backups. `--deploy` opts into the configured server deployment; it does
not publish Pages. `--publish --notes-file docs/release/v0.0.1-notes.md` pushes
the tag and directly creates a GitHub Release; **do not use it for the staged
Pages workflow below**, which publishes only after Pages succeeds.

## Stage and publish through Pages

This checkout supplies `.github/workflows/release.yml` and
`tools/release_pages.py`. The helper and workflow define artifact names and
identity checks.

```sh
python3 ./tools/release_pages.py prepare v0.0.1 \
  --package "$PWD/build/releases/v0.0.1/package" \
  --engine "$PWD/build/releases/v0.0.1/engine" --out build/pages-upload
gh release create v0.0.1 --draft --target "$(git rev-parse HEAD)" \
  --title 'Digimon World Horizon 0.0.1' \
  --notes-file docs/release/v0.0.1-notes.md
gh release upload v0.0.1 build/pages-upload/horizon-package.tar.gz \
  build/pages-upload/horizon-engine.tar.gz build/pages-upload/horizon-checksums.json
git push origin refs/tags/v0.0.1
```

Confirm `gh` targets the intended public repository. Creating a draft may create
a lightweight remote tag if the annotated tag is absent; the final push must
leave an annotated remote tag. Resolve any mismatch before continuing. The
workflow runs on the tag push, or can be retried with `workflow_dispatch` and the
same tag once assets exist. It downloads the three prepared assets, validates
hashes and exact version/date/commit identity without executing the bundle,
assembles and tests the static site, deploys with Actions Pages, then publishes
the draft. It never builds the game in CI and never receives discs or caches.
Configure Settings → Pages → GitHub Actions and permit release tags in the
`github-pages` environment before the run. Confirm custom-domain/DNS/HTTPS setup
using [the release guide](releasing.md).

**Notes handoff:** the current `release_pages.py build` generates
short metadata-only notes and the final workflow overwrites the draft notes.
Until that helper is updated to retain this checked-in notes file, restore the
player notes after workflow success:

```sh
gh release edit v0.0.1 --notes-file docs/release/v0.0.1-notes.md
```

## Verify the live result

1. Require successful build, deploy and publish jobs; check the release is public
   and has the three prepared assets. Download the package into a fresh directory,
   unpack it and run the README's standalone apply with the four player inputs.
   Compare its image SHA-1 with the corresponding package manifest output.
2. Open `https://dw1horizon.com/` in a fresh desktop browser profile. Fetch
   `https://dw1horizon.com/engine/current.json` with caching disabled and compare
   `release_tag`, `release_version`, `release_date`, and engine `version` with the
   staged candidate. Check that footer, language selection and all four disc
   requirements work and that plan/pack requests have no 404 or cross-origin errors.
3. Build using the USA base plus the three source discs, save the resulting CUE/BIN,
   and compare the BIN SHA-1 against `manifest.json`. Load the CUE in an emulator
   configured for original 2 MB RAM; confirm v0.0.1 title, language selection,
   new game and Continue. Stop the emulator. Other source-region outputs have
   independent manifest pins; do not expect identical whole-disc hashes across regions.
4. Check in a second fresh profile after deployment; an old service worker may
   cache the previous page/engine. Reload before building across releases. Only
   the latest engine is served on Pages; older engine archives remain release assets.

## What may be skipped

Keep the default release gates for the final merged/tagged commit. Do not skip
package verification, standalone applies, heap checks or the candidate browser
check merely because another branch passed. The sealed path above carries the
mandatory heavy proof forward only for the exact tracked tree and retained hashes. `--skip-browser` exists, but is safe
only when the exact candidate package/engine has already passed the same browser
SHA-1 comparison and that evidence is retained. Optional emulator corpus checks
and new-save recording can be done before cut day and omitted from the default
run. Own-server deployment and direct publication are unnecessary for Pages.
Recorder reuse is automatic only for identical graph inputs. Do not force older
records after source or bundle changes; the build cache must retain its
own input validation. Tag/version changes require either the sealed restamp proof above or a full build.
