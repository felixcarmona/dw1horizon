# Digimon roster roadmap

This proposal prioritizes which playable Digimon species to polish or add, and in what order. As a proposal, sections 1–3 are suggested as the v1.0 focus (not a release commitment), expanding the original roster with species from shows and games around its global release. Sections 4–5 outline possible later additions.

## Status key

Track each area independently: **Art** covers models, textures and animations; **Techniques** covers assigned attacks, finishers, effects and learning; **Evo requirements** covers parents, raising conditions and evolution routes.

| Status | Meaning |
|---|---|
| not started | No implementation is recorded for this area. |
| in-progress | Work exists or has begun, but playability in this area has not yet been confirmed. |
| Needs a hand-authoring decision | No model is identified in the supported-disc catalogs; inclusion needs an agreed authoring plan. |
| configured | The species JSON defines partner data and raising routes; in-game acceptance remains open. |
| playable | Usable in the game; polish, balancing or broader validation remains. |
| completed | Finished, reviewed and validated for the intended role, with no planned work remaining in this area. |

Statuses are a snapshot of `origin/main` (`60e7b22a`) on 2026-11-05; the [species JSON](../content/species/) is the source of truth. `configured` records source inspection, not a new playtest; existing `playable` reports are retained, and techniques remain in-progress pending separate validation.

The [decision log](decisions.md#species--levels) records current level and model changes. Current model work includes constant body scale for 67 imports and a victory/praise rework across 28 species. These repairs do not close each species' remaining art checks.

## Purpose and release boundary

Use the [ideas backlog](ideas.md) for unselected suggestions and the [decision log](decisions.md) for established behavior and its reasons. This roadmap proposes roster priorities; it does not replace either document.

Prioritize complete, recognizable families, then supporting species and regional variety. Follow the numbered order within each section; fixes to released content take precedence.

Use assets from **Digimon World 1, Digimon World 2, Digimon World 2003 and Digital Card Battle**. The project can also use hand-authored assets, as with the babies. Other candidates need a model from those discs or an agreed hand-authoring plan before implementation.

Availability checks use the [import lists](../content/imports/lists/), [conversion specs](../content/imports/specs/) and [source-game inventory](reference/imported-species.md#the-source-games). A missing catalog entry is not a queued import: it needs a hand-authoring decision. Imperialdramon Fighter and Paladin modes have DW2003 source models but no species records; source availability alone does not establish partner fit.

## Acceptance criteria

Scope acceptance to the intended role: partner by default, or explicitly enemy/NPC first. A finished NPC is not a finished raisable partner; track each area separately and record non-applicable checks.

1. **Reproducible asset.** Record the source or authoring recipe, tool revision and content identity. Rebuild from supported player-owned discs and permitted authored inputs; distribute recipes and authored changes, not donor assets.
2. **Art review in game.** Check silhouette, textures, deformation, scale and contacts through movement, care, training, evolution and battle states used by that role.
3. **Techniques and requirements.** Validate learning/equipping, attacks, finishers, effects and hit timing. Test parents, raising conditions, competing routes, item evolution and rebirth as applicable, plus save/reload. Compare balance with existing peers; test NPC/enemy roles in their actual encounters.
4. **Options and 2 MB fit.** Check NEW DIGIMON and EXTENDED STORY on/off, partner fallback/restoration, difficulty and 20/60 FPS as applicable. Verify model, animation and heap limits in dense scenes and transitions on the standard 2 MB PlayStation configuration; record emulator settings and optional extra headroom separately.
5. **Evidence.** Link the tested commit, build settings, commands, results and reviewed images/video. Check peers affected by shared changes and revisit acceptance when relevant assets, data or runtime code change.

## Decisions to make before expanding the commitment

Discuss these proposals alongside the [ideas backlog](ideas.md); check the [decision log](decisions.md) before changing existing gameplay or option contracts.

- **v1.0 roster (open):** whether sections 1–3, in this order, become the v1.0 goal is still to be agreed; listing a species does not promise it. Sections 4–5 outline later post-game expansions.
- **Profiles:** define the supported roster, balance and story combinations. NEW DIGIMON OFF currently limits species; it does not undo the unconditional care/economy rebalancing described in [balance.md](mods/balance.md). EASY/NORMAL is a combat multiplier, not a complete classic/expanded ruleset switch.
- **Save semantics:** keep species IDs and mod-owned flags stable. Document fallbacks, restored partners, retained recruitment and story-removal behavior using the existing [options](mods/options.md) and [compatibility](mods/compatibility.md) contracts. Test two saves with different options, not only one save round trips.
- **Library boundary:** demonstrate one standalone mini-mod using a polished family, one encounter/resident and a save round trip with the beta story disabled. This is a practical acceptance test for the framework claim. A new story, a fusion system and every late boss can remain separate consumers of that library.

## Open for discussion

These points are left open on purpose; nothing here is decided by this roadmap.

- **Kotemon → Dinohyumon → Kyukimon → SlashAngemon** is not the current evolution tree (the existing parents differ). Treat it as a proposed
  tree change that needs its own review, not as validation of existing routes.
- **Show families versus raising routes.** Some rows describe anime families (for example Pegasusmon from Patamon) that differ from the
  game's actual parents. Changing parents needs a separate tree review under the existing tree rules (every raisable Rookie with enough
  Champions, every Champion with Ultimates, every Ultimate with a Mega route).
- **Armor and DNA forms** are listed as roster species with ordinary routes; they don't imply a fusion or armor-evolution system, which would
  be a separate design proposal.
- **Regional bosses, residents and the standalone mini-mod** are story work, separate from roster polish; the original story keeps every
  recruit, service and route.
- **Candidates without a model in the four supported discs** need an agreed hand-authoring plan and a 2 MB feasibility check before they are
  scheduled; the hand-made babies don't prove that larger Digimon are feasible.
